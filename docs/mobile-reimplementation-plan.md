# KILO Strength 移动端重新实施计划

## 1. 结论与边界

移动端必须以 `web-prototype` 的当前实现为唯一产品基线，不再复用 `E:\fitness app` 根目录旧 BetterCoach Flutter 工程的页面结构。Android 先完成可安装、可离线使用、可与 Web 逐项对照的正式客户端；iOS 复用 Flutter 业务与主界面，但灵动岛、锁屏实时活动和必要的系统交互使用 Swift、SwiftUI、ActivityKit 与 WidgetKit 原生实现。

“原封不动移植”在本项目中的含义：

- 页面层级、导航名称、信息顺序、主次按钮、弹层路径、文案和业务规则一致。
- 颜色、字号、间距、圆角、图标、动作图片、状态色和动效节奏使用同一套 token。
- Web 中每个可操作按钮、表单、筛选、空态、错误态、离线态和低置信度状态在移动端都有对应行为。
- 只对系统能力做平台适配，例如相机、文件选择、通知、锁屏、后台上传和权限申请；不得借适配之名改变产品结构。

## 2. 产品与商业校验

- 目标用户：已有规律训练基础、在健身房单手操作手机的男性力量或增肌训练者。
- 当前替代方案：Hevy、Strong 等训练记录工具，外加手动拍摄、教练点评或通用 AI 问答。
- 改变理由：把计划、逐组记录、动作识别和有依据的解释放进一次连续训练流程，减少切换工具和重复录入。
- 最小可用路径：打开应用 -> 选择已保存计划或空白训练 -> 开始训练 -> 完成一组 -> 休息计时 -> 保存记录。
- 主要指标：打开应用后开始训练率、到达第一组的时间、训练保存完成率、识别报告查看率、分析后再次拍摄率。
- 失败代价：如果只做近似 UI 或只实现 happy path，Web 验证结果无法迁移，后续数据模型、识别流程和 iOS 系统能力都要再次返工。

商业判断：这一版最应提升“打开应用后完成第一组并最终保存训练”的比例；首页唯一主操作、计划详情中的明确开始按钮和训练中的低干扰布局共同负责推动该指标。

## 3. 设计读取

页面类型：移动端专业训练工具。目标用户：有训练基础的男性用户。视觉语气：浅色、硬核、克制、精密仪器感。设计家族：沿用现有 KILO Performance Bay 体系，Android 遵循 Material 3 的系统行为，iOS 遵循 Apple HIG 的系统行为，但不改变 KILO 的品牌视觉。

- `DESIGN_VARIANCE = 3`：结构必须稳定、可预测，不重新设计已验证页面。
- `MOTION_INTENSITY = 4`：只保留页面切换、弹层、完成组反馈、进度和粒子背景。
- `VISUAL_DENSITY = 5`：训练页低密度，动作库、记录和计划编辑保持工具型密度。
- 设计 token 以 `DESIGN.md` 和 Web 实际 CSS 为准。`design-system/kilo-strength/MASTER.md` 中与 `DESIGN.md` 冲突的紫色游戏风内容不得进入移动端。

## 4. 新目录与技术结构

```text
strength-pro/
  web-prototype/                 # Web 验收基线，保持可运行
  backend-mock/                  # 当前接口模拟
  contracts/                     # 冻结后的 JSON Schema 与状态枚举
  mobile/
    app/                         # Flutter Android/iOS 主应用
      lib/
        app/                     # 路由、主题、依赖注入、平台能力入口
        domain/                  # 与平台无关的实体和用例
        data/                    # Drift、本地优先仓储、API 客户端
        features/                # 按 Web 页面分区
        platform/                # Pigeon/MethodChannel 的窄接口
      android/                   # Kotlin 通知、后台任务、相机适配
      ios/                       # Runner 与原生桥接
    ios-live-activity/           # SwiftUI + ActivityKit/WidgetKit 扩展
    golden/                      # Web 基线图和 Flutter golden 图
    integration_test/            # 端到端主路径
```

Flutter 负责 Android/iOS 的主业务界面和共享状态，避免双端逻辑漂移。Drift 负责本地训练计划、训练草稿、训练记录、动作备注、识别任务元数据和 AI 会话。原生代码只拥有系统能力，不重复业务规则。

## 5. 首先冻结的契约

在写移动端页面前完成以下工作：

1. 从 `types.ts` 提取正式实体：动作、组、训练动作、模板、训练记录、休息计时、识别任务、聊天消息和设备状态。
2. 从 `state.ts` 和 `main.ts` 提取状态机，明确允许的转换、撤销和恢复行为。
3. 为当前全部 `data-action`、`data-form` 和 `data-field` 建立 `web-mobile-parity.md`，每项必须有 Flutter 页面、用例、测试编号和完成状态。
4. 冻结 API：分析任务创建/查询/结果/确认、AI 回答、AI 计划草稿、动作库和计划库。
5. 所有实体使用稳定 UUID、`revision`、`updatedAt`、`deletedAt` 和来源版本，为后续同步保留冲突处理能力。

## 6. 功能迁移批次

### P0：基线与可视化验收夹具

- 固定当前 Web 构建版本和 320、375、414、768、1024、1440 宽度截图。
- 录制主路径的页面、弹层、键盘、返回和状态变化。
- 导出 KILO token、Phosphor 图标映射、动作图片和许可声明。
- 建立超长中文、长英文、200% 字体、空数据、错误和离线压力数据。

验收：任何移动端页面都能指出对应 Web 截图、状态和交互清单。

### P1：应用壳、导航与视觉系统

- 实现主页、训练、记录、动作库、识别、AI、我的七个入口；计划仍属于训练内的二级路径。
- 复刻 Web 顶栏、底栏、安全区、页面宽度、背景、粒子层、按钮和弹层。
- 支持系统字体缩放、深链返回、键盘、屏幕阅读器和 Reduce Motion。

验收：七个入口、所有空态和主弹层在 Android 真机与 golden test 中通过。

### P2：本地优先训练闭环

- 已保存计划、官方计划、空白训练、模板文件夹和计划编辑。
- 动作增删改序、热身组、工作组、失败组、超级组、重量、次数范围、RPE 和独立休息。
- 开始/暂停/恢复训练计时，逐组完成，批量修改，杠片计算器，PR 提示，保存和恢复草稿。
- 计划详情只浏览；只有“开始训练”才创建实时训练并启动计时。

验收：飞行模式下可以完成“建计划 -> 训练 -> 保存 -> 再次打开记录”的完整流程，杀进程后草稿可恢复。

### P3：记录、日历与进步

- 完整月历、未来排期、改期、移除、补录、编辑和删除训练。
- 记录详情、训练量、有效组、PR、动作趋势、肌群分布和长期目标。
- 完成、已安排、已安排但未完成同时使用图标/文字和颜色表达。

验收：跨月、闰日、时区变化、删除恢复、长训练名称和空历史均通过测试。

### P4：动作库与私人资源

- 迁移 32 个首发动作、筛选、搜索、自定义动作、详情、机位、提示和加载模式。
- 复用现有动作图片；库、计划、实时训练三个 scope 的备注和私密链接独立保存。
- 图片缺失、链接无效、超长备注和离线资源都有可恢复状态。

验收：Web 中每个动作库入口和计划/训练内动作入口均能到达相同详情与编辑路径。

### P5：动作识别

- 原生相机/文件选择、机位指导、文件校验、上传进度、后台任务和取消/重试。
- BetterCoach 仍通过接口适配；客户端不把模型实现写死在页面中。
- 完整实现 idle、ready、processing、complete、low-confidence、offline 和失败恢复。
- 报告包含逐次重复、置信度、纠错提示、关联训练、保存提示和再次分析。

验收：Mock API 与真实 BetterCoach 测试环境使用同一客户端契约；应用重启后任务可继续查询。

### P6：有依据的 AI 聊天

- 复刻 Web AI 界面、对话记录、输入区、发送等待、引用详情和训练数据授权。
- 客户端只调用 `/v1/coach/answer`，DeepSeek key、检索和引用校验全部留在服务端。
- 理论主张必须带论文或可靠来源；无证据、来源冲突和医疗风险有明确状态，不允许模型伪造引用。
- 默认不上传视频；只有用户明确授权时发送最小训练或识别摘要。

验收：引用可追溯、授权可撤销、离线对话可查看、失败消息可重试，未授权请求不包含训练摘要。

### P7：系统级体验

Android：

- Kotlin 前台服务承载训练/休息计时，通知显示当前动作、组和剩余时间。
- Android 13+ 按使用时机申请通知权限；通知可暂停、跳过或结束休息。
- WorkManager 处理可恢复上传，CameraX/系统选择器处理拍摄和媒体授权。

iOS：

- Flutter 主应用通过 Pigeon 或窄 MethodChannel 发送计时状态。
- Swift/SwiftUI ActivityKit 扩展实现灵动岛和锁屏 Live Activity。
- 使用 AppIntent 提供暂停、跳过和结束等受系统支持的交互；系统版本不支持时退化为普通通知。
- Widget/Live Activity 不直接读 Flutter 内存，只读取 App Group 中的最小共享状态。

验收：主应用退出前台后计时不漂移；系统重启、权限拒绝和低电量模式均有明确降级。

### P8：发布级验证

- `flutter analyze`、单元测试、Widget 测试、golden 测试和集成测试全部通过。
- Android 至少覆盖 API 26、API 33 和当前目标 API 的真机/模拟器。
- 视觉宽度覆盖 320、375、414、768、1024、1440；检查 200% 字体和横竖屏切换。
- 每页检查 loading、empty、error、success、disabled、focus、pressed、keyboard 和 back 行为。
- 检查 `scrollWidth` 等价问题：无横向溢出、按钮不越界、弹层不超出 viewport、长文本不破坏布局。
- 生成签名配置之外的 Debug APK 供验收；通过功能矩阵后再配置正式签名与商店发布。

## 7. 必须建立的测试门槛

- 交互覆盖率：Web 功能矩阵 100%，不能以“移动端暂不支持”跳过普通业务功能。
- 视觉基线：关键页面 golden 差异需要人工确认；不能只依赖组件测试。
- 数据可靠性：断网、杀进程、升级数据库和重复提交不丢训练记录。
- 计时准确性：使用绝对结束时间计算，前后台切换不累计漂移。
- 隐私：视频和训练摘要默认不上传；权限拒绝后仍可使用不依赖该权限的功能。
- 可访问性：44dp 触控目标、可读标签、焦点顺序、颜色非唯一信号、200% 文本可用。

## 8. 明确禁止的做法

- 禁止从根目录旧 BetterCoach Flutter 工程复制页面作为起点。
- 禁止先做几个相似页面后宣称“已迁移”。
- 禁止在 Flutter 和原生层各维护一套训练状态。
- 禁止把 Web 的弹层流程随意改成新页面，或把新页面随意压成弹层。
- 禁止在客户端保存 DeepSeek API Key、论文检索凭据或服务端知识库。
- 禁止在未完成真实浏览器/真机截图对照前交付 UI。

## 9. 推荐执行顺序与阶段出口

严格按 `P0 -> P1 -> P2 -> P3 -> P4 -> P5 -> P6 -> P7 -> P8` 推进。每个阶段只有在功能矩阵、截图对照、异常状态和本地持久化测试同时通过后才能进入下一阶段。Android 在 P2 结束时应已有第一版可安装 APK，在 P6 结束时形成完整功能候选版；iOS 主应用与共享业务同步推进，ActivityKit 扩展在 P7 接入。

最终“完成”定义不是成功编译，而是：当前 Web 原型的全部功能与布局均能在 Android 上逐项复现，iOS 共享功能一致，系统级能力按各平台原生规范工作，并且所有差异都有明确、可验证的系统原因。
